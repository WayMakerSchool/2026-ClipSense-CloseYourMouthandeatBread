# 설계: 보행 신호 데이터 소스 — API 모듈 + 이중 판단 구조

**작성일:** 2026-07-13
**대상:** Clip sense 실제 제품(프로토타입 단계)의 보행 신호 데이터 계층
**범위:** 이번 설계는 (1) 서울 T-Data 실시간 보행신호 API 연동 모듈과 (2) 그것이
카메라 비전과 만나 최종 판단을 내리는 이중 판단 구조까지다. Flutter 앱 골격,
ESP32 하드웨어, GPS/위치, 피드백(음성·햅틱)은 이 문서의 범위가 아니다(후속 스펙).

---

## 1. 배경과 문제 정의

시각장애인용 보행 신호 안내 기기는 "지금 이 순간 보행 신호등이 초록인가, 몇 초
남았는가"를 알아야 한다. 이 데이터의 출처를 확정하기 위해 한국의 공개 API/데이터를
5개 각도(경찰청/UTIS, 서울 TOPIS, 전국 C-ITS, 지자체 횡단보도 데이터셋, 음향신호기/
시각장애인 기존 서비스)로 전수 조사했다.

### 조사 결론 (실측 기반)

- **실시간 보행 신호 색을 주는 공개 API는 서울 T-Data 하나뿐이다.**
  - 서비스: "신호제어기 신호 잔여시간 정보서비스" (제공기관 C-ITS/미래첨단교통과)
  - 실시간 보행신호 상태 + 잔여시간을 8방위별로 제공.
  - 제약: **서울 C-ITS 대상 교차로 한정**(전국 커버 아님). 프로토타입에선 무관.
- **경찰청 실시간 신호정보 시스템**(강릉→전국 확대)은 실시간 색+잔여를 주지만
  **공개 API가 아니다**(티맵·카카오 등과 B2B 협약). → 중장기 제휴 타깃.
- **세종/부산/하남 등 지자체 "횡단보도 조회 API"의 신호시간 필드는 정적 설정값**
  (신호주기 지속시간)이지 실시간 현재 색이 아니다. 사용 불가로 확정.
- 따라서 **전국 어디서나 동작 가능한 유일한 소스는 카메라 비전**이다.

### 역할 확정

- **카메라 비전(메인 A):** 전국 어디서나 눈앞의 보행등을 직접 읽음. API 없는
  지역을 커버. 이미 Python 데모(`detector.py`)가 이 일을 한다.
- **서울 T-Data API(메인 B):** 서울 커버 구역에서 실시간 색+잔여시간을 줌.
  초기 데모의 핵심 시나리오("빨간불 N초 남음"을 음성 안내)를 그대로 실현.
- 둘 다 1급(메인)으로 개발한다. 서울에선 서로 교차검증하고, 서울 밖에선
  카메라 단독으로 동작한다.

## 2. 실측으로 확정된 API 사실 (2026-07-13 실제 호출)

> 아래는 발급된 개발 키로 실제 엔드포인트를 호출해 얻은 값이다. 문서 설명이 아니라
> 실물 응답이다.

- **엔드포인트:**
  `https://t-data.seoul.go.kr/apig/apiman-gateway/tapi/v2xSignalPhaseTimingFusionInformation/1.0`
- **인증 파라미터:** `apiKey` (대문자/소문자 `apikey` 둘 다 200 응답 확인)
- **주요 요청 파라미터:** `type=json`, `itstId`(교차로 ID, 예: `1537` 실동작 확인),
  `pageNo`, `numOfRows`
- **응답 구조:** 최상위가 **레코드 배열**(JSON list). `header/body` 래핑 없음.
- **보행신호 상태 필드:** `{방위}PdsgStatNm` (8방위: nt/et/st/wt/ne/se/sw/nw).
  값 크기 30자 문자열.
- **보행신호 잔여 필드:** `{방위}PdsgRmdrCs`. **단위 1/10초**
  (실측 예: `241` = 24.1초, `725` = 72.5초).
- **시각 필드:** `trsmUtcTime`(전송 UTC epoch ms) → 신선도(stale) 판정에 사용.
- **교차로/식별:** `itstId`, `dataId`(예: `SPAT-...`), `eqmnId`(장비ID).

### 상태값 enum (실측 — SAE J2735 표준 영문 코드)

| 실제 반환 문자열 | 의미 | 색 매핑 |
|---|---|---|
| `protected-Movement-Allowed` | 보호 이동 허용 = 보행 초록 | **GREEN** |
| `permissive-Movement-Allowed` | 허용 이동 = 초록(조건부) | **GREEN** |
| `protected-clearance` | 보호 정리(현시 종료 임박) | **CLEARANCE**(초록 점멸) |
| `permissive-clearance` | 허용 정리 | **CLEARANCE** |
| `stop-And-Remain` | 정지 후 대기 = 보행 빨강 | **RED** |
| `null`/빈값 | 해당 방위에 신호 없음/무데이터 | **UNKNOWN** |
| (위 목록 외 처음 보는 값) | 미지 | **UNKNOWN**(추측 금지) |

### 아직 확인 못 한 것 (정직하게 명시)

- `permissive-*`와 `protected-*`의 안전상 구분이 실제로 필요한지: 프로토타입에선
  둘 다 같은 색으로 매핑하되, 향후 실주행 데이터로 재검토.
- 잔여시간 `0` 또는 비정상 큰 값(감응신호 무효)의 실제 표현: 실동작에서 관찰 후
  임계값 확정 필요.
- 호출 rate limit(개발계정 트래픽 한도): 명세 미기재. 폴링 주기 설계 시 보수적으로.

## 3. 아키텍처 개요

```
                         ┌─────────────────────────┐
   서울 T-Data API  ───▶ │  signal_api (얇은 번역기) │──┐
   (실시간 SPaT)         │  응답→{색,잔여초,신선도}  │  │
                         └─────────────────────────┘  │
                                                       ▼
                                            ┌──────────────────────┐
                                            │   judge (판단 엔진)    │
   카메라 프레임    ───▶ ┌──────────────┐   │  AND 규칙 + Fail-Safe │──▶ 결과
   (전국 어디서나)       │ vision       │──▶│  둘 다 GREEN & 잔여충분 │   {WALK|WAIT|
                         │ (detector.py)│   │  → WALK, 아니면 WAIT   │    UNKNOWN}
                         └──────────────┘   └──────────────────────┘
```

- **`signal_api`** — 서울 API를 호출해 표준 형태로 번역만 한다. 판단하지 않는다.
- **`vision`** — 기존 `detector.py`의 색 판정을 표준 형태로 감싼다. 판단하지 않는다.
- **`judge`** — 두 소스를 받아 **AND 규칙**으로 최종 결정을 낸다. 안전의 중심.
- 출력·음성·GPS·하드웨어는 이 설계 범위 밖(judge의 결과를 소비할 뿐).

### 데이터 흐름의 핵심 원칙

각 모듈은 **하나의 책임**만 지고, **표준 신호 판정 객체**로만 대화한다. 이렇게
경계를 좁혀야 "API가 죽으면 카메라 단독" 전환이 judge 안에서 한 줄로 끝난다.

## 4. 표준 데이터 구조

세 모듈이 공유하는 단일 표현. (Dart로 구현하되 여기선 개념 스키마로 기술)

```
SignalReading {
  color:     GREEN | RED | CLEARANCE | UNKNOWN   // 필수
  remainSec: double?      // 남은 초. 모르면 null. 색과 독립적으로 채워짐
                          // (색은 GREEN인데 잔여초만 모를 수도, 반대일 수도 있음)
  source:    API | VISION // 어디서 왔는지
  freshMs:   int          // 이 값이 몇 ms 전 것인지 (신선도)
  raw:       string?      // 디버그용 원문(예: 'protected-Movement-Allowed')
}
```

- `color`는 4-값 고정. **VISION과 API가 동일한 enum을 쓴다** → judge가 단순 비교.
- `remainSec`는 색과 독립. API는 `RmdrCs/10`, VISION은 (있으면) 숫자 판독기 값.
- `UNKNOWN`은 "모른다"는 1급 상태다. 절대 GREEN으로 추측되지 않는다(브리프 원칙 4).

## 5. 모듈별 상세 설계

### 5.1 `signal_api` — 서울 T-Data 번역기

**책임:** `(itstId, 방위)` → API 호출 → `SignalReading(source=API)` 반환.

**색 매핑:** §2의 실측 enum 표를 그대로 코드화. **화이트리스트 방식** —
명시적으로 아는 문자열만 GREEN/RED/CLEARANCE로, 나머지 전부 UNKNOWN.

**정직성 안전망:**
- 처음 보는 상태 문자열 → UNKNOWN (raw에 원문 보존해 로깅).
- `trsmUtcTime`이 현재보다 임계(예: 2초) 이상 과거 → UNKNOWN (stale).
- HTTP 오류/타임아웃/파싱 실패 → UNKNOWN (예외를 삼켜 앱을 죽이지 않음).
- 잔여초 비정상값 → 색은 유지, remainSec=null.

**방위 선택:** 교차로엔 8방위 보행신호가 있다. 사용자가 "어느 횡단보도를 건너는가"
= 어느 방위인가를 알아야 한다. 이 매핑(GPS 진행방향→방위)은 **위치 모듈의 책임**
이며 이 설계 범위 밖. `signal_api`는 방위를 인자로 받기만 한다. 프로토타입에선
방위를 수동/설정으로 고정해 테스트한다.

**키 관리:** API 키는 **환경변수/설정파일**로만 주입한다. 소스코드·저장소에
하드코딩 금지. (현재 노출된 개발 키는 프로토타입 후 재발급 권장.)

**폴링:** judge가 필요할 때 호출(pull). 연속 안내 중에는 주기 폴링(주기는 rate
limit 확인 후 확정, 잠정 1~2초). 응답을 캐시해 과호출 방지.

### 5.2 `vision` — 기존 검출기 어댑터

**책임:** 카메라 프레임(또는 기존 데모의 상태) → `SignalReading(source=VISION)`.

- 기존 `detector.py`의 RED/GREEN/GREEN_BLINK/UNKNOWN을 표준 4-값으로 매핑
  (GREEN_BLINK → CLEARANCE). 이미 존재하는 로직을 감싸는 얇은 층.
- `remainSec`는 숫자 판독기(`digits.py`)가 신뢰할 때만 채우고, 아니면 null.
- 이 어댑터는 검출 알고리즘을 바꾸지 않는다 — 표현만 표준화한다.

### 5.3 `judge` — 이중 판단 엔진 (안전 핵심)

**책임:** `SignalReading(API), SignalReading(VISION)` → 최종 `Decision`.

**Decision = WALK | WAIT | UNKNOWN**

**규칙 (AND / Fail-Safe):**
```
WALK 조건 (모두 만족해야):
  1) api.color   == GREEN
  2) vision.color == GREEN
  3) 잔여시간 충분: min(있는 remainSec들) >= 사용자_보행_소요_추정
  4) 두 소스 모두 fresh (stale 아님)
위 중 하나라도 불만족  → WAIT   ("잠시 기다리세요")
두 소스 모두 UNKNOWN    → UNKNOWN ("신호를 확인할 수 없습니다")
```

- **핵심:** 둘이 갈리면(API=GREEN, VISION=RED 등) → 항상 **WAIT**. 절대 WALK 아님.
- **한 소스만 있는 경우(서울 밖 = API 없음):** 정책 결정 필요 →
  프로토타입 기본값 = "가용한 소스가 GREEN이고 조건 충족 시 WALK 허용"으로 하되,
  이 완화가 안전한지는 §7 오픈 이슈로 남긴다(데모에선 카메라 단독 WALK 필요).
- 상태 전이엔 디바운스/쿨다운을 두어 깜빡임에 흔들리지 않게 한다(기존 상태머신 재사용).

**"잔여시간 충분" 판정:** 사용자 보행 속도(설정 또는 기본 1.0 m/s)와 횡단 길이로
소요 시간을 추정하고, 남은 초가 그보다 크면 충분. 횡단 길이를 모르면 보수적
고정 임계(예: 7초) 사용. (횡단 길이 데이터는 후속 위치 모듈에서.)

## 6. 테스트 전략

- **`signal_api` 단위 테스트:** 실측 응답 JSON을 고정 픽스처로 저장하고, 각 enum이
  올바른 색으로 매핑되는지, 미지 문자열·stale·null·HTTP오류가 전부 UNKNOWN으로
  떨어지는지 검증. (네트워크 없이 실행 가능해야 함 → 응답을 목킹.)
- **`judge` 단위 테스트:** 두 소스의 모든 조합(GREEN/RED/CLEARANCE/UNKNOWN ×
  fresh/stale × 잔여충분/부족)에 대해 WALK가 나오는 경우가 오직 "AND 만족" 뿐임을
  검증. 특히 **의견 불일치 시 절대 WALK 안 나옴**을 명시적으로 테스트.
- **통합(수동):** 실동작 교차로(`itstId=1537`)를 폴링하며 색/잔여가 사람이 보는
  실제 신호와 일치하는지 대조.
- 기존 비전 테스트 스위트(`scripts/`)는 그대로 회귀 방지로 유지.

## 7. 오픈 이슈 (구현 전/중 해소)

1. **한 소스만 가용할 때 WALK 허용 정책** — 서울 밖(API 없음)에서 카메라 단독
   WALK를 허용해야 데모가 되지만, 이중검증의 안전 이점이 사라진다. 프로토타입에선
   허용하되, 실제 제품에선 카메라 신뢰도 임계를 높이는 등 보강 필요.
2. **GPS 진행방향 → 8방위 매핑** — 위치 모듈 몫. 이 설계는 방위를 인자로 받음.
3. **API rate limit / 폴링 주기** — 개발계정 트래픽 한도 확인 후 확정.
4. **`permissive` vs `protected` 세분화** 필요성 — 실데이터로 재검토.
5. **API 키 재발급** — 노출된 개발 키는 프로토타입 종료 후 교체.

## 8. 이번 설계에 포함하지 않는 것 (후속 스펙)

- Flutter 앱 골격(백그라운드 동작, 앱 상태관리)
- GPS/위치 기반 교차로·방위 선택
- 피드백 계층(네이티브 TTS, 상황별 햅틱, 목적지 락온)
- 고대비 접근성 UI
- ESP32-S3 클립 카메라 하드웨어 및 Wi-Fi 스트리밍
- 접근 차량 소리 감지(마이크)

이들은 각각 별도 설계·계획 사이클로 진행한다.
