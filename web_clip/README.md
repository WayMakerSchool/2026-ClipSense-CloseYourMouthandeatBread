# 10/19 클립 → 웹 연결 실험

별도 HTML/JavaScript 화면과 Python 로컬 서버다. Flutter 앱 자동 웹 변환이 아니다.
기존 `detector.py`와 `SignalStateMachine`, `clip_snapshot.py`, 엄격 `judge.evaluate()`를
재사용한다. 사진 수신·판독·음성 요청은 구현했고, **실제 클립 사진 갱신·실제 소리·영상은
현장에서 확인해야 완료**다. 실험 결과를 미리 완료로 쓰지 않는다.

## 실행

**보드 없이 먼저 연습:**

```bash
.venv/bin/python scripts/run_web_demo.py
```

http://127.0.0.1:5173 에서 시작 버튼을 누른다. 합성 빨강 → 초록 → 신호 없음이
각 12초씩 바뀐다. 토큰·보드가 필요 없으며 화면과 기록에 **SIM**을 표시한다.
판독·대기 안내·음성·재실행·기록 저장 연습용이고 실제 클립 검증은 아니다.
한 장면을 고정하려면 `--scene red`, `--scene green`, `--scene none`을 사용한다.
SIM과 실제 연결 서버는 같은 포트를 사용하므로 하나를 Ctrl+C로 종료한 뒤 다른 것을 실행한다.

**보드를 연결한 뒤:**

저장소 루트에서 기존 `.venv` 사용:

```bash
.venv/bin/python clip_web.py --clip http://192.168.0.52
```

Mac의 Chrome에서 **http://127.0.0.1:5173** 을 열고 **시작 · 음성 켜기**를 누른다.
토큰은 기존 `~/.clipsense/device_token`을 사용한다. 없으면 터미널에서 숨김 입력:

```bash
read -rs 'CLIP_DEVICE_TOKEN?기기 토큰: '
export CLIP_DEVICE_TOKEN
.venv/bin/python clip_web.py --clip http://192.168.0.52
```

토큰을 URL·채팅·소스에 쓰지 않는다. `401/403`이면 토큰 확인 후 서버를 재실행한다.
서버 종료는 `Ctrl+C`. 페이지 새로고침 또는 재실행 후 시작 버튼과 실제 소리를 다시 확인한다.
화면의 중지는 **이 브라우저의 화면 갱신·음성**을 멈춘다. 보드 사진 요청까지 멈추려면 서버를 종료한다.

다른 기기에서 열 경우 Mac·보드·휴대전화가 같은 팀 전용 Wi-Fi에 연결되어야 한다.
다음은 Mac의 IP가 `192.168.0.69`인 경우의 예다. IP는 접속할 때 다시 확인한다.

```bash
ipconfig getifaddr en0
.venv/bin/python clip_web.py --clip http://192.168.0.52 \
  --listen 0.0.0.0 --allow-host 192.168.0.69
```

휴대전화에서는 `http://192.168.0.69:5173`을 연다. 기본 설정은 Mac 자신만 접속 가능하다.
공용망·공개 호스팅으로 노출하지 않는다. 기기·브라우저가 달라지면 사진·소리를 다시 확인한다.

## 접속 구조

```text
Chrome의 http://127.0.0.1:5173
  └─ GET /api/frame (사진 JPEG + 같은 사진의 판독 + 메타데이터, no-store)
       └─ Python → http://192.168.0.52/capture
                    X-Clip-Device-Token (서버에만 있음)
```

브라우저는 보드 주소를 직접 fetch하지 않는다. 웹·사진 요청이 같은 origin이므로
이 경로에 보드의 CORS 허용 origin이나 custom-header preflight를 추가할 필요가 없다.
HTTPS 웹 페이지에서 HTTP 보드를 직접 읽는 구조도 사용하지 않는다.
브라우저 보호 설정·CORS·인증서 검증을 끄지 않는다.
관련 브라우저 동작: [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS),
[Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Mixed_content).

- 서버는 시작할 때 고정한 보드 origin만 요청하며 리디렉션을 따라가지 않는다.
- 기본 250ms 간격, 요청 제한 800ms, 최대 512KiB QVGA(320×240) JPEG.
- JPEG·필수 헤더·프레임 진행·재부팅·사진 나이를 검사한다.
- 같은 프레임은 연속 판독 횟수나 신선도를 늘리지 않는다. 역행은 버린다.
- 2초가 넘은 사진을 숨기고 확인 불가/대기로 돌아간다. 브라우저도 별도 타이머로 만료시킨다.
- 실패·재부팅·사진 공백 뒤에는 판독 이력을 다시 쌓는다.
- `SIM`, `LAPTOP/laptop-upload`, 알려진 `OV…` 센서를 분리 표시한다. 센서 헤더만으로
  물리적 촬영을 입증할 수 없으므로 **클립과 움직이는 물체, 웹을 함께 찍은 연속 영상**이 필요하다.
- 토큰은 브라우저/기록 JSON에 포함하지 않는다. 기록은 메모리 안에 유지하며 내려받기로 저장한다.

## 고정 판독 기준

규칙 버전: `clip-web-rules-2026-10-19-v1`. 학습 AI 모델이 아니다.
시작 시 읽은 `config.json`과 판독 소스·웹 소스의 SHA-256을 기록에 포함한다.
설정 파일을 고쳤다면 서버 재실행 후 새 해시로 다시 측정한다.

| 항목 | 값 |
|---|---|
| ROI | 중앙 가로·세로 각 25% (QVGA에서 80×60), 사진의 노란 상자 |
| 빨강 HSV | H 0–12 또는 165–180, S≥55, V≥45 |
| 초록 HSV | H 35–100, S≥45, V≥45 |
| blob 면적 비율 | 0.005–0.6 (이전 검출색 이탈 임계는 0.6배) |
| 원형도 / 종횡비 | ≥0.12 / 0.45–2.2 |
| 형태 연산 / 안정화 | 5×5 열기·닫기 / 연속 8개의 새 프레임 |
| 사진 만료 | 보수적 사진 나이 >2,000ms |
| 최종 판단 | 실제 API 미연결 → WAIT 또는 UNKNOWN, 항상 기다리기 |

`--roi-fraction 0.5`처럼 시작 시 ROI를 바꿀 수 있으나, **측정 중에는 고정**한다.
ROI·카메라 위치가 달라지면 동일한 실험이라고 쓰지 말고 기록을 나눠 저장한다.
화면은 프레임 판독과 연속 판독 확정을 나누어 보여준다. 전환 중에는 이전 확정색으로 안내하지 않는다.
빨강·초록이 동시에 잡히면 기존 검출기의 면적 우선 규칙을 그대로 사용한다.
신호등이 아닌 색 물체가 판독될 수 있으므로 이 실험만으로 현장 인식 성능을 주장하지 않는다.

## 오늘 순서와 증거

1. **연결:** 화면의 클립 주소·촬영 출처·프레임 번호·마지막 수신 확인.
   물체를 움직이고 클립과 웹이 같이 보이는 연속 영상 촬영. SIM/노트북 중계이면 그대로 표시.
2. **판독:** 빨강/초록/신호 없음 장면을 각각 8초 이상 유지.
   장면 선택 → 메모 → 판독/확정/최종 안내 확인 → `현재 결과 기록`.
3. **음성:** 시작 버튼 → 소리 직접 듣기 → `방금 안내 들었어요` → 결과 기록.
   화면의 음성 요청/시작/종료는 브라우저 이벤트다. **실제로 들렸다는 증거는 아니다.**
   사용자 청취 확인과 소리 포함 영상으로 확인한다. `다시 듣기`로 현재 최종 안내를 재생한다.
4. **재실행:** 중지/재시작 또는 새로고침 후, 사진·화면·실제 소리를 다시 확인.
   **기록 내려받기**로 JSON 저장. 페이지 새로고침 전에 저장한다.

JSON에는 기기 브라우저 UA, 페이지 origin, 보드 origin, 고정 기준/해시, 프레임 순번·출처·사진 해시,
기대 장면, 판독, 최종 안내, 음성 이벤트, 사용자 청취 시각, 시작/중지 기록을 담는다.
사진 원본이나 영상은 JSON에 저장하지 않는다. 영상은 OS 화면 녹화/다른 기기로 따로 남긴다.
한국어 음성은 브라우저·OS의 [SpeechSynthesis](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis)를
사용하므로 실제 사용할 기기에서 지원·음성·음량을 확인한다. 미지원/실패는 화면에 표시한다.

두 학생 설명:

- 다림: “서버가 받은 같은 JPEG를 웹 사진과 HSV·모양 판독에 씁니다. 색 마스크,
  면적·원형도·종횡비를 확인하고, 새 사진 8장이 연속 같은 색일 때 확정합니다.”
- 폴: “판독이 초록이어도 실제 API와 남은 시간이 없으면 기다리라고 합니다.
  사진이 오래되거나 끊겨도 대기하고, 화면 글과 실제 들린 말을 따로 비교합니다.”

## 테스트

```bash
.venv/bin/python scripts/test_clip_web.py
node scripts/test_clip_web_client.cjs
```

Python은 실제 로컬 소켓으로 SIM 계약·웹 응답을 검사한다. Node는 브라우저 API를 대체해
재시작 후 이전 응답 무효화, 클라이언트 만료, 음성 이벤트와 청취 확인 구분을 검사한다.
통과해도 실제 보드 촬영·브라우저 소리·연속 영상 검증을 대신하지 않는다.

## 연결되지 않을 때

- `192.168.0.52` 같은 보드 IP: Arduino 시리얼 모니터 115200 baud → 리셋 → `ip` 행 확인.
  노트북 IP와 보드 IP는 서로 다르다. 주소를 브라우저에 넣어 토큰 없이 열면 인증 오류가 날 수 있다.
- `연결 불가`: 보드 전원, 같은 Wi-Fi, 시리얼 IP, 펌웨어 HTTP 서버 상태 확인.
  ping 성공은 사진 서버 성공을 뜻하지 않는다.
- `토큰 거부`: 저장된 기기 토큰을 보드의 토큰과 대조하고 서버 재실행. 토큰을 화면에 공개하지 않는다.
- `QVGA JPEG 오류`: 보드 프로필이 320×240인지 확인. 오류를 가짜 사진으로 대체하지 않는다.
- `신호 없음`: 노란 ROI 안에 램프가 있는지, 크기가 너무 작거나 큰지 확인.
- 소리 없음: 시작/다시 듣기, 브라우저 음소거·기기 출력·음량·한국어 음성 확인.

## 10/22 추가: 실제 보드 · 작은 교차로 · 신호등 찾기

- 실보드(XIAO ESP32S3 Sense, OV3660)에서 사진 수신 확인. 학교 공용 Wi-Fi는 신호가
  -85dBm 이하라 사진 본문이 멈췄고, 휴대폰 핫스팟(-52~-65dBm)에서 40회 중 38회,
  중앙값 281ms로 받았다. 핫스팟을 다시 켜면 보드·Mac IP가 바뀐다.
- `--signal-api`: 신호 API를 0.5초마다 읽어 `judge.evaluate`의 엄격 AND로 판단한다.
  다음 조회 전까지 받은 잔여시간을 흐른 시간만큼 줄인다. 실제 T-Data 주소면 5분보다
  자주 묻지 않는다(2026-10-01 정책). 안내 문구에 남은 초를 넣지 않는다 — 매초 바뀌면
  음성이 계속 다시 읽는다. 남은 초는 화면에만 표시한다.
- `scripts/mini_intersection.py`: 모의 T-Data API와 신호등 화면(회색 배경, 검은 몸체,
  위 빨강·아래 초록, 오른쪽 빨간 7-세그먼트 숫자)이 한 시계로 돈다. ok/freeze/down
  버튼으로 API 장애를 시연한다. 화면과 기록에 SIM을 표시하며 도로 시험이 아니다.
- `--vision head` (`signal_head.py`):
  - 어두움 기준 = 사진 밝기 중간값 × 0.6 (최대 120). 휴대폰 화면의 검정이 카메라에서
    V≈80으로 뜬다(배경 V≈196).
  - 숫자 빨강 기준 S≥80·V≥130. 기본값(S≥100·V≥80)은 JPEG 색 번짐으로 합성 0~99 중
    70개를 못 읽었다. 실측 숫자 획은 S≈99·V≈166.
  - 숫자 간격이 숫자 폭의 80% 미만이면 '12' 같은 두 자리가 붙는다.
  - 숫자 판독값은 (숫자 − 1초 − 사진 나이)로 보수적으로 쓰며, judge에서 API보다 짧을 때만 반영된다.
- 한계: 실제 카메라에서 인식이 켜졌다 꺼졌다 한다. 원인(몸체 놓침/색 날아감/연속 확정 끊김)을
  작은 교차로 API를 정답 라벨로 삼아 실제 프레임을 모아 확인할 예정이다.
